# Mission Brief: Bringing AirLink Panel's Addon System to Blueprint-Level Power

You are working inside **`panel-main`** (AirLink Panel — a Node/Express/Prisma/EJS game-server management panel). Your job is to take its existing **addon system** and rebuild it into a genuinely powerful extension framework: one that gives addon authors the same breadth of capability that **Blueprint** (the extension framework for Pterodactyl Panel) gives its extension authors, while updating every internal contract that currently blocks that, and closing every security gap that arbitrary, repo-owned, addon-loading code currently has.

**You do not have access to the Blueprint (`framework-main`) source code.** That is intentional. Part 1 of this document describes, in full and exact detail, everything about Blueprint's design that is relevant to this work — its manifest format, its extension points, its lifecycle, its permission model, its security posture — so you do not need the original source to understand what you're replicating. Read it carefully before writing any code. Where something in Blueprint is an artifact of its own stack (PHP/Laravel/Blade/React/webpack) and has no business being ported literally into a Node/Express/EJS/Prisma codebase, that is called out explicitly so you adapt the *capability*, not the *mechanism*. Do not copy code patterns from this document's PHP/React description verbatim into TypeScript — there is no PHP/React code here to copy; everything is prose description of behavior, by design, so that what you build is native to this stack.

## What "done" looks like

An addon author working against the new system should be able to do everything a Blueprint extension author can do — manifest-declared identity and versioning, granular per-extension capability toggles an admin can flip without disabling the whole addon, real database migrations with rollback, a documented set of UI injection points (not just menu items, real markup/wrapper injection), static asset hosting, scheduled/recurring tasks, console-triggerable commands, a private per-addon settings store, dependency declarations, and a safe, validated install/update/uninstall lifecycle — and they should be able to do it idiomatically, in TypeScript, against Express and Prisma, without needing to know anything about Blueprint or PHP.

Every existing, already-published addon (anything built against the current `(router, api) => void` contract documented in `docs/addons.md`, `docs/addon-quickstart.md`, `docs/addon-migrations.md`, and `storage/addons/README.md`) must keep working unmodified after your changes. This is a real external compatibility boundary — there are addons in the `airlinklabs/addons` community registry built against the current contract — so backward compatibility here is not optional scope-creep, it's a hard constraint.

## Ground rules

1. **Adapt, don't port.** Blueprint physically rewrites Laravel/Blade/React source files at install time and rebuilds a webpack bundle. AirLink Panel is a long-running Node process that dynamically `require()`s addon code and renders server-side EJS on every request. These are different execution models. Anywhere this document describes a Blueprint mechanism, treat it as a description of a *capability* to replicate, not a sequence of shell/sed commands to transliterate. Several sections below explicitly flag where panel-main's architecture can do something more simply (e.g. true runtime hot-reload) than Blueprint's heavier compile-and-patch approach — prefer the simpler, more idiomatic version.
2. **Addon code is trusted code, not sandboxed code — in both systems.** Blueprint extensions are arbitrary PHP classes; AirLink addons are arbitrary Node modules with a live `PrismaClient` and full `require()` access. Neither system pretends to sandbox third-party code. Don't invent a false sense of security in the UI or docs. The actual security work here is: validating everything that crosses a real trust boundary (the manifest on disk, the remote store payload, user-submitted settings/forms), eliminating concrete bugs that let one addon clobber another or leak state across installs, locking down the one place arbitrary shell commands already run (the community-store installer), and being honest in the documentation about what is and isn't isolated.
3. **Verify before you trust this document.** Part 0 below tells you exactly which files to read first. This document was written from a real audit of the current `panel-main` code, but the agent who wrote it (also a Claude model) could not give you live access to confirm nothing has drifted since. If something here contradicts the code you're looking at, the code wins — flag the discrepancy in your own working notes and proceed from reality.
4. **Resolve uncertainty into contracts, not shims.** Where you find an existing pattern that papers over missing validation (a `JSON.parse(...) as SomeInterface` with no runtime check, a closed string-literal union that can't represent third-party data, a duplicated read-and-parse routine copy-pasted three times) fix the contract at its source rather than adding another defensive layer around it. This is elaborated on in the skills section below.
5. **Everything you add must be typed, validated at its real boundary, and documented.** No `any` smuggled in through a new API surface. No new manifest field that isn't schema-validated. No new admin-facing capability that isn't written up in the docs listed in Part 5.

## Part 1 — What Blueprint actually does (so you don't need its source)

This section describes Blueprint's extension system capability by capability. Each subsection ends with an **Adaptation note** translating that capability into something that belongs in this stack. Treat the capability as the requirement; treat the mechanism (file-patching, Blade, webpack, Artisan) as background only — it explains *why* Blueprint built it that way, not what you should build.

For context: Blueprint extensions are distributed as a single `.blueprint` file (a zip with a different extension). Installing one is a CLI operation (`blueprint -i extension.blueprint`) that unpacks the zip, reads a `conf.yml` manifest, and then — this is the structurally important part — **physically copies and text-patches files into the host Laravel/React application's own source tree**, then triggers a `composer`/`artisan`/`yarn build` style rebuild. Nothing about an installed extension is "loaded dynamically" at runtime the way a Node `require()` is; the extension's code becomes, literally, part of the compiled application until it's removed. Every capability below is a consequence of that design.

### A. Manifest identity, naming, and versioning

Every extension ships a `conf.yml` with an `info` block: a display `name`, a machine `identifier`, a `description`, a `version` string, an optional `icon`, an optional `author`, an optional `website`, and a `target` (the Blueprint engine version the extension was authored against).

The `identifier` is the single most load-bearing field in the whole system. It is validated against a strict rule before anything else happens: lowercase letters and digits only, no longer than 48 characters, and it cannot literally be the string `blueprint` (reserved for the framework's own self-hosted dashboard extension). Every other generated artifact is namespaced by this identifier — generated PHP class names, generated route names, the extension's own subfolder under the framework's private storage, its public asset folder, its settings-table key prefix. Get the identifier validation wrong and you get collisions and overwrites; this is treated as a security property, not just a style rule.

`target` is informational/compatibility metadata, not a hard gate: at install time Blueprint compares its own running engine version against the extension's declared `target` and, when they don't line up, it **warns rather than blocks** — the extension still installs, but a flag (effectively "is this target current") gets set, and a legacy-compatible placeholder mode kicks in for older `target` values so the extension's templated source still gets sensible substitutions even though it was authored against an older engine. Blueprint chooses availability over strictness here.

`version` is the extension's own version. Blueprint doesn't enforce semver comparisons against it as an install gate; it's primarily display metadata and the value compared against a remote "latest version available" lookup (see section J) to power an "update available" indicator in the admin UI.

**Adaptation note:** Replicate the identifier discipline exactly — it's good design independent of Blueprint. Replicate the "warn, don't hard-block" posture for version/target mismatches as the default, because addon code is just as trusted/full-privilege here as a Blueprint extension is there, so a mismatch is a stability concern, not a security one — but since this is a fresh implementation, also expose an admin-configurable strict mode that does hard-block, since some operators will reasonably want that. Use a real semver-range comparison (the project doesn't currently depend on a semver library; decide whether to add a small, well-known one or hand-roll the narrow comparison you actually need) against the panel's own version (already present as `version` in `package.json`) rather than a string-equality check.

### B. Granular, admin-revocable capability flags

Beyond a single enable/disable switch, Blueprint extensions have a small set of named permissions an *administrator* controls independently of whether the extension itself is enabled. The two real ones that exist today are: whether the extension's "wrap the entire admin layout" component is allowed to run, and whether its "wrap the entire client dashboard" component is allowed to run. These are stored as simple booleans in the host application's own settings table (keyed by `blueprint::extensionconfig_<identifier>_<key>`), surfaced through a small admin form per extension, and checked at render time before the corresponding wrapper component is mounted. The point: if an extension's dashboard-wrapping component ships a bug that breaks every page, an admin has an escape hatch that doesn't require fully disabling (and thereby losing the rest of) the extension.

There is a closely related, separate mechanism: extensions that add server-facing UI can be scoped to only show up for certain server "egg" (game/server-type template) IDs, again as an admin-editable per-extension setting defaulting to "all eggs," persisted the same way.

Separately — and this one is *not* an admin-facing toggle, it's a manifest-declared, install-time mechanism specific to Blueprint's file-patching install process — extensions declare a small set of `flags` in `conf.yml` (a comma-separated list) that change how the *installer itself* behaves: whether to skip the placeholder-substitution pass entirely, whether to force the legacy (older-target) placeholder substitution rules even on a current-target extension, whether to skip rebuilding the compiled frontend bundle after install (useful when an extension makes no frontend changes, to save a slow rebuild), whether to keep Laravel's cached config (skip clearing `artisan config:cache`), and a couple of flags that escalate a custom install/update/removal script to run with elevated file-ownership privileges instead of the webserver user. These flags exist specifically because Blueprint's install process is a multi-step, privileged file-system operation; none of them describe a capability an extension *has* at runtime, only how it gets installed.

**Adaptation note:** Replicate the *first* mechanism (admin-revocable, per-addon capability toggles, independent of the master enable switch) generalized beyond just "wraps admin layout / wraps dashboard" to cover every risky or layout-affecting capability you build below (any slot/wrapper registration, any raw-SQL migration, any scheduled task). Replicate the egg-scoping idea too — AirLink's server templates are the `Images` model; an addon's server-facing UI contribution should be scopable to specific image IDs the same way, admin-editable, defaulting to "all." Do **not** replicate Blueprint's install-time flags (`ignorePlaceholders`, `forceLegacyPlaceholders`, the `developer*` escalation flags) literally — they're solving problems (placeholder substitution, privileged file ownership, cache invalidation across a multi-step shell install) that don't exist in a `require()`-based loader. If you find you need an analogous "this addon's install/enable does something slow or risky, skip it on a fast-path reload" concept, design it fresh for this architecture rather than naming it after Blueprint's flags.

### C. Frontend extension points ("slots") — the flagship capability

This is the part of Blueprint that does the most work, and the part you should put the most care into translating well, because it's also the part where Blueprint's actual mechanism is the *least* relevant to copy.

The Pterodactyl React dashboard's own source code has, scattered throughout its real component tree, a deliberate set of fixed import statements that resolve to a path alias, `@blueprint/...`, which webpack resolves to a real (but normally near-empty) folder. For example, the terminal/console page imports a component from `@blueprint/components/Server/Terminal/CommandRow`; the file that import resolves to, before any extension is installed, looks like a near-empty stub: it renders nothing, but contains two literal marker comments — one where new `import` statements get appended, one where new JSX element references get appended. There are dozens of these stub files scattered through the dashboard's component tree, one per named extension point, with names like `BeforeContent`, `AfterContent`, `AdditionalItems`, `DropdownItems`, `CommandRow`, `ResourceLimits`, `NavigationLinks`, `Attribution` — each living at the specific location in the component tree (e.g. `Server/Terminal/...`, `Server/Files/...`, `Server/Databases/...`, `Authentication/Container/...`, `Server/Schedules/List/...`) that corresponds to the real page/section it augments.

When an extension's `conf.yml` declares a `dashboard.components` directory, Blueprint's installer walks that directory (which the extension author structures to mirror the slot names, e.g. `dev/.dashboard/components/Server/Terminal/CommandRow/index.tsx`), and for each component file it finds, it (1) copies the extension's own component file into its own subfolder under the resolved `@blueprint` path, and (2) **text-inserts** one `import` line and one JSX-element line into the corresponding stub file, right at its two marker comments. Multiple extensions targeting the same slot just keep appending more lines at the same two markers — that's how more than one extension can render into the same slot simultaneously. Then the whole dashboard gets rebuilt with `yarn build` so the now-larger stub files actually get compiled in. Removal does the textual inverse (strip the extension's lines back out) and triggers a rebuild again.

Separately, `dashboard.wrapper` and `admin.wrapper` are not slot-list items, they're singular: a component an extension declares here gets imported as the literal **outermost wrapper around the entire client dashboard (or entire admin panel) React tree** — every page, all the time, until an admin (per section B) turns that specific extension's wrapper permission off. `dashboard.css` / `admin.css` work the same way for a single global stylesheet.

On the backend side, `admin.view` lets an extension ship whole new Blade view files (i.e. genuinely new admin pages, not just injections into existing ones), and `admin.controller` ships the PHP controller backing them; Laravel auto-discovers and routes these because they land in conventional directories, combined with the extension's own declared route file (see section D).

**Adaptation note — this is the important one.** Do not attempt to literally patch EJS source files with marker comments and rebuild anything; panel-main has no build/bundle step for its server-rendered views the way Pterodactyl's SPA does, and trying to mimic a compile-time text-patch onto an interpreted-at-request-time template engine would be strictly worse than building this natively. What you should build instead is a **runtime slot registry**, parallel in spirit to (and possibly literally extending) the existing `uiComponentStore` in `uiComponentHandler.ts`:

- A fixed, documented, enumerable set of slot identifiers — your own list, scoped to the real pages this panel actually has (dashboard home, per-server console, per-server files, per-server backups, per-server settings, per-server startup, the admin server-edit page, the login/auth pages, etc.), each with a clear semantic (`before-content`, `after-content`, `additional-items`, `dropdown-items`, where they genuinely make sense for this UI — don't cargo-cult Blueprint's exact slot names if a page doesn't have an equivalent section).
- Addons register against a slot at load time with a render function, the same way they currently register a `SidebarItem` or `ServerMenuItem` — except a slot's contribution is **markup**, not a structured item (an addon can call its own `api.renderView(...)`/`res.render`-equivalent to produce that markup from its own EJS partial, or hand back a string directly).
- A small number of new, deliberate include points get added to the *existing* core EJS templates at exactly the slot locations you've enumerated — this is the entire scope of changes to core view files, and it should be a small, fixed, reviewable diff, not a sprawling one.
- Two genuine "wrap everything" hooks (`dashboard.layout.wrapper`, `admin.layout.wrapper`) at the base desktop/mobile layout templates, gated by the per-addon, admin-revocable capability toggle from section B — this is the direct functional equivalent of Blueprint's `dashboard.wrapper`/`admin.wrapper`, and is genuinely worth building because it's the only way an addon could do something like inject a global banner, a global keyboard-shortcut overlay, or a global analytics snippet.
- One concrete engineering risk to resolve, not paper over: EJS templates render synchronously by default once you call the top-level `res.render`. If an addon's slot contribution needs `await`-able work (a DB read, an API call) to produce its markup, decide and document whether slot render functions are awaited *before* the main page render call (computing a map of `slotId -> renderedHtml` up front and passing it in as locals) or whether the installed EJS version's async render mode is used end-to-end. Don't guess at the installed `ejs` package's exact async API from memory — check `node_modules/ejs`'s actual current behavior/docs in this environment before committing to an approach, since pinning the wrong assumption here will produce subtly broken or silently-empty slots under load.

### D. Backend extension points (routes, controllers, new pages)

`conf.yml`'s `requests` block lets an extension ship new PHP "app" classes (services, jobs, anything under `app/`), new controllers, new Blade views, and — the part that matters most — merges into three *separate* route files: one for Pterodactyl's admin-facing "Application API," one for the user-facing "Client API," and one for plain browser-facing "Web" routes. All of this exists because Laravel autoloads/auto-registers anything dropped into its conventional directories; Blueprint is just placing files where Laravel already expects to find them, then appending route-registration lines to the right route file.

**Adaptation note:** Express has no directory-convention autoloading, so this isn't a gap panel-main needs to fill with new machinery — the *existing* `registerRoute(path, router)` / single mounted `Router` per addon already covers "ship new pages and new endpoints," and there's no Pterodactyl-style 3-way Application-API/Client-API/Web split to replicate since this codebase's admin pages, user pages, and JSON API endpoints already coexist in ordinary `Router`s (see `src/modules/admin/addons.ts` for an existing example that freely mixes `res.render` and `res.json` in the same router). The real gap here isn't capability, it's two things: (1) addons currently have to reach into `src/handlers/utils/auth/authUtil.ts` and `src/handlers/utils/api/apiValidator.ts` with relative `require()` paths to get session-auth or API-key-auth middleware for their own routes, which is undocumented and fragile against future refactors of those paths; expose stable references to `isAuthenticated`, `apiValidator`, and `csrfProtection` directly on the `AddonAPI` surface so addons compose real auth into their own routers without knowing the internal file layout. (2) the documentation should show, explicitly, an addon that registers *two* routers — one EJS web router and one JSON-only `/api/<slug>` router guarded by `apiValidator('addon.<slug>.something')` — since today's docs only ever show the single-web-router case and a reader could reasonably believe that's the only option.

### E. Static asset hosting

`data.public` declares a folder inside the extension that gets copied to a path under the host application's public webroot and served at a predictable URL, `/extensions/<identifier>/...`. This is how an extension ships its own images, fonts, or any asset it wants linked directly from a `<link>`/`<img>`/`<script>` tag rather than going through application code.

**Adaptation note:** `docs/addons.md` and `storage/addons/README.md` already describe a `public/` folder as part of the documented addon structure, but `src/handlers/addonHandler.ts` never actually serves it — confirm this against the current code (Part 0) and, if it's still true, this is a documented-but-unimplemented feature, not a new one. Implement it: serve each enabled addon's own `public/` directory at a namespaced path (e.g. `/addon-assets/<slug>/...`), mounted and unmounted in lockstep with the addon's router in `loadAddons`/`unloadAddon`, and resolve the addon's real path with `fs.realpathSync` to confirm it's still inside that addon's own directory before serving from it (closes a symlink-based path-escape route a malicious or sloppily-packaged addon could otherwise use).

### F. Database migrations and a private per-extension settings store

Blueprint extensions ship ordinary Laravel migration files in `database.migrations`; the framework copies them into the host's `database/migrations` directory and runs `artisan migrate`. Laravel migrations are inherently reversible (an `up()` and a `down()` per file), so removal can roll them back. Separately, Blueprint exposes a tiny global helper (`$blueprint` in every Blade view and the base extension library) with `dbGet`/`dbSet`/`dbGetMany`/`dbSetMany`/`dbForget`/`dbForgetMany`/`dbForgetAll` methods, which read and write arbitrary key-value pairs into the host's existing generic `settings` table, namespaced under `blueprint::extensionconfig_<identifier>_<key>`. This is how an extension persists its own configuration (anything from "is feature X on" to arbitrary JSON blobs) without ever needing its own SQL table or its own migration for simple cases.

**Adaptation note:** AirLink's addon migrations (Part 0; `docs/addon-migrations.md`) are forward-only raw SQL strings with no `down`, applied via `prisma.$executeRawUnsafe` and tracked in an `AddonMigration` table, with no transaction wrapping the DDL execution and the bookkeeping insert together, and — critically — no lifecycle hook that runs when an addon is fully uninstalled, so its custom tables and its `AddonMigration` rows are simply abandoned on disk forever. Fix all of this (full spec in Part 2, B6). Separately, AirLink has **no generic key-value table at all** — `settings` is a single fixed-column global-settings row, not a key-value store — so there is currently no equivalent of Blueprint's `dbGet`/`dbSet` for addon authors; the documented pattern today (`docs/addon-migrations.md`) pushes every addon author toward writing their own raw-SQL custom table even for storing one boolean. Add a real generic per-addon settings table and expose it on the `AddonAPI` (Part 2, B3/B5) — this directly removes the temptation toward unnecessary raw SQL for the common case.

### G. Lifecycle hooks: install, update, removal

Blueprint's CLI install script does meaningfully more than "copy files": it detects whether the extension is already installed (a flat list file under the framework's private storage), and if so treats this as an *update* — it diffs which generated artifacts (a public folder, a console command) are no longer declared and removes the stale ones, it preserves the extension's existing settings-table values across the version bump, and — if the extension's manifest opted in via the escalation flags from section B — it runs a custom `update.sh` script the extension author ships, with an explicit warning that this script runs with elevated privileges and arbitrary shell access. Removal is similar: it prompts the operator for an explicit confirmation (clearly warning that a custom removal script, if present, runs arbitrary code) before running the extension's own `remove.sh` hook (if any) and then deleting every file/route/migration-record/public-asset the extension owns, in a fixed order. Both install and removal take an exclusive lockfile for the duration, so two install/removal operations can't interleave and corrupt the framework's bookkeeping.

**Adaptation note:** This is a real, valuable capability gap in AirLink today — `toggleAddonStatus`/`reloadAddons`/the uninstall route in `src/modules/admin/addons.ts` have no equivalent of "let the addon's own code run something when it's enabled/disabled/updated/uninstalled." Build a small, optional lifecycle-hook contract (full spec in Part 2, B7) that an addon can opt into, and call it at exactly the right moments: once on first install, on every version bump (passing the previous version so the addon can decide what changed), on enable, on disable, and — most importantly, since this is the gap that currently leaks tables and migration rows forever — on full uninstall, *before* the framework deletes the addon's files or its `AddonMigration` records, so the addon gets a real chance to clean up after itself. Replicate the "ask for explicit confirmation before destructive removal" UX in the admin UI (a confirmation modal, not a bare button) — this one part of Blueprint's removal flow translates directly and cheaply. Replicate the lockfile concept too: this Node process is single-process, so an in-memory async mutex serializing install/enable/disable/uninstall operations is sufficient — you don't need a filesystem lockfile, just something that prevents two of these operations from interleaving against the same addon (or against the shared `AddonMigration` bookkeeping) if two admin requests land close together.

### H. Console commands and scheduled tasks

`data.console` plus a `Console.yml` sub-manifest lets an extension declare one or more entries, each with a command signature, a description, a path to a PHP file containing the command's logic, and an optional interval (`daily`, `hourly`, `everyMinute`, etc.). At install time, Blueprint generates a real Laravel Artisan command class from a template (so the extension's command becomes genuinely callable as `php artisan <signature>` from a terminal) and, when an interval is declared, a matching entry in Laravel's task scheduler, so it also runs unattended on that cadence.

**Adaptation note:** AirLink has no general-purpose registered-subcommand CLI today (just a handful of ad hoc one-off scripts under `scripts/`), so full parity here means building two things, not porting one: (1) a way for an addon to register a named command with a handler function, exposed on the `AddonAPI`; and (2) a delivery mechanism for actually invoking it. The minimum viable delivery mechanism is an admin-UI button per registered command (boot the app, find the addon, call the handler, stream the result) — straightforward and consistent with how this admin panel already does everything else. True CLI parity (something genuinely callable from a terminal, e.g. a `pnpm run addon:command <slug> <command> [...args]` entry point that boots a minimal context, loads just that one addon, and invokes the handler) is a meaningfully better match for what Blueprint actually provides and worth building if time allows — design the registration contract so either delivery mechanism, or both, can sit on top without addon authors caring which one is wired up. For the scheduled/cron half: there's no cron-style dependency currently installed; decide between adding one well-known, audited library or implementing the narrow subset you actually need (fixed-interval re-firing is enough for most realistic addon use cases; full calendar-style cron expressions are a nice-to-have, not a requirement) and back it with a single in-process scheduler that addons register against (`api.schedule.register({ id, ... , handler })`). Whatever you build, it must (a) catch and log handler errors without ever crashing the host process, and (b) clear and re-create an addon's previously-registered timers whenever that addon is reloaded — `reloadAddons` already fully reloads every addon on every call (Part 0), and a scheduler that doesn't deduplicate by a stable id will leak a duplicate timer on every single "Reload addons" click.

### I. Dependency declarations between extensions

Checked directly: Blueprint's `conf.yml` schema (`info`, `admin`, `dashboard`, `data`, `database`, `requests`) has **no field for one extension to declare a dependency on another extension.** Don't describe this as a Blueprint feature when you write your own docs — it isn't one. What Blueprint's installer *does* check is whether required system binaries/Node tooling are present on the host machine, which is a different concern (environment prerequisites, not inter-extension dependencies).

**Adaptation note:** Genuine inter-addon dependency declarations (addon B requires addon A, optionally with a version range, with load order resolved by topological sort instead of directory-iteration order, and a clear admin-facing error when a dependency is missing or disabled) are good general plugin-system design and worth adding to panel-main even though they're not feature parity with anything Blueprint has. Build it, but label it in your own documentation as a new capability beyond Blueprint, not a port — accuracy here matters for anyone who later compares the two systems.

### J. Distribution, the community store, and update notifications

End users install Blueprint extensions either by uploading a `.blueprint` file directly, or — relevant here — Blueprint's own dashboard (itself shipped as a self-referential extension) talks to a remote API to list and fetch extensions, caching small bits of remote metadata (notably the latest version available) in a dedicated SQL table so the admin UI can show an "update available" indicator per installed extension without re-fetching on every page load.

**Adaptation note:** AirLink already has a more elaborate version of the "remote store" half of this — `src/modules/admin/addons.ts` already lists, installs, and uninstalls addons from a real GitHub-backed community registry (`airlinklabs/addons`), with a streaming installer that clones a repo and runs an allow-listed set of setup commands. That part is *already ahead* of where Blueprint's own extension distribution model is in some respects (Blueprint requires a manual file upload; this panel has a live registry browser). What's missing is the "update available" half: cache each installed addon's latest-known-remote-version (refreshed periodically, not on every page load) and surface it as a badge in `/admin/addons`, and — more importantly — close the concrete security gap in the existing installer described in Part 2, B13 ("Hardening the existing install pipeline") before adding anything new on top of it.

### K. The trust/security model, stated plainly

Worth being explicit about, because it shapes how to think about every "make it secure" item in Part 3: Blueprint extensions are not sandboxed. A PHP class shipped inside a `.blueprint` file can do anything any other PHP code running inside that Laravel process can do — read any file the webserver user can read, make arbitrary outbound requests, query the full database. The safety net Blueprint actually relies on is: extension installation is an explicit, admin-only, deliberate action (never something a non-admin user can trigger); identifiers and paths are validated to prevent one extension's install from clobbering another extension or the host application's own files; destructive operations (removal, anything with a custom shell-script hook) require explicit confirmation and are clearly labeled as running arbitrary code; and the whole thing is auditable (a flat installed-extensions list, a settings-table namespace per extension). AirLink addon code has exactly the same actual privilege level — a live `PrismaClient`, full `require()` access, the ability to mount routes anywhere. Don't write documentation or UI copy that implies addons are sandboxed or that installing one is safe by default; the correct framing, matching Blueprint's own honesty about this, is "installing an addon is equivalent to installing a dependency: only do it from a source you trust, because it runs with the same privileges as the rest of the panel."

## Part 2 — Concrete specification: Addon System v2 for panel-main

Each item below names the exact contract to change, says why (tying back to Part 1 where it's replicating a Blueprint capability, or to Part 0 where it's fixing an existing bug), and gives acceptance criteria. Code blocks are illustrative sketches to make the contract concrete — adapt naming, error handling, and exact shape to match the rest of the codebase's conventions; they are not meant to be pasted in verbatim.

### B1. Manifest schema v2 — replace the unchecked cast with a real, validated, single-source-of-truth schema

Today: `loadAddons`, `toggleAddonStatus`, and `reloadAddons` in `addonHandler.ts` each independently do `JSON.parse(fs.readFileSync(packageJsonPath, 'utf-8'))` and assign the result to an `AddonPackageJson`-typed variable with no runtime check at all. Fix this once.

Required:

- One Zod schema, defined once, that is the single source of truth for the manifest shape. Derive the TypeScript type from it (`z.infer<typeof addonManifestSchema>`); do not hand-write a parallel interface.
- One function, used by every call site that currently re-implements the read+parse (all three in `addonHandler.ts`, plus the install-from-store flow in `src/modules/admin/addons.ts` if it ever needs to read a manifest), that reads the file and parses it through the schema, returning a typed, validated result or a clear, addon-name-attributed error. This is the boundary; once data has passed through it, the rest of the codebase trusts the shape (`boundaries-validate-internals-trust`).
- New/changed fields on top of the existing `name, version, description?, author?, main?, router?, enabled?, migrations?`:
  - `identifier` (new, required for new manifests; if absent, default it to the folder name for backward compatibility with every existing addon that has never had to declare one — see the back-compat checklist in Part 4). Validate with the same discipline Blueprint applies (Part 1, section A): lowercase letters, digits, and hyphens only, bounded length, and a denylist of reserved words that would collide with core panel routes or concepts (`admin`, `api`, `auth`, `login`, `static`, `assets`, the literal string `core`, etc. — derive the actual denylist from real route prefixes already in use rather than guessing). The manifest's declared `identifier`, when present, must equal the folder name exactly — refuse to load an addon where they diverge, since that divergence is exactly the kind of confusable-identity bug the identifier rule exists to prevent.
  - `engines.panel` (new, optional): a version-range string compared against the running panel's own version (already available as `version` in this project's `package.json`) at load time. Default behavior on mismatch is to load anyway with a clearly surfaced admin-facing warning (Part 1, section A); make strict blocking an admin-configurable setting, not the unconditional default.
  - `permissions` (new, optional): an array of permission strings this addon wants to register, each required to be namespaced as `addon.<identifier>.*` (validated against this exact addon's own identifier at parse time — an addon cannot declare a permission outside its own namespace; this is the enforcement half of the permission-contract fix in B2).
  - `capabilities` (new, optional): a small, explicit object of booleans for anything risky or layout-affecting this addon does — at minimum whether it registers a dashboard/admin layout wrapper, whether it runs raw SQL migrations, whether it registers scheduled tasks. This is what the admin-revocable toggles in B14 (admin UI) are driven from; it's the generalized version of Blueprint's `adminlayouts`/`dashboardwrapper` switches (Part 1, section B).
  - `settingsSchema` (new, optional): a small declarative array describing addon-specific admin-configurable settings (key, a primitive type, a label, a default), used to auto-render a generic settings form (B5) instead of every addon author hand-building EJS forms for simple config.
  - `dependencies` (new, optional): other addon identifiers (optionally with a version range) this addon requires to be installed and enabled (Part 1, section I — this is a new capability, not a Blueprint port; document it as such).
  - `migrations` (existing field, extended): each entry gains an optional `down` SQL string alongside the existing `name`/`sql` (B6).
  - Keep `router` exactly as-is in meaning (still the single mount path for the addon's router) but validate it doesn't collide with a denylist of reserved top-level path prefixes, and that it isn't empty/`/` unless that's genuinely intended.

```ts
// Illustrative shape only — adapt naming/structure to match this codebase's conventions.
const addonManifestSchema = z.object({
  name: z.string().min(1),
  identifier: z.string().regex(/^[a-z0-9-]{1,48}$/).optional(), // optional only for back-compat; see Part 4
  version: z.string().min(1),
  description: z.string().optional(),
  author: z.string().optional(),
  main: z.string().optional(),
  router: z.string().optional(),
  enabled: z.boolean().optional(),
  engines: z.object({ panel: z.string() }).partial().optional(),
  permissions: z.array(z.string()).optional(), // namespace-checked against `identifier` after parse, not in the schema itself
  capabilities: z.object({
    wrapsDashboard: z.boolean(),
    wrapsAdminLayout: z.boolean(),
    runsRawSql: z.boolean(),
    registersSchedules: z.boolean(),
  }).partial().optional(),
  settingsSchema: z.array(z.object({
    key: z.string(),
    type: z.enum(['string', 'number', 'boolean']),
    label: z.string(),
    default: z.union([z.string(), z.number(), z.boolean()]).optional(),
  })).optional(),
  dependencies: z.array(z.object({ identifier: z.string(), range: z.string().optional() })).optional(),
  migrations: z.array(z.object({ name: z.string(), sql: z.string(), down: z.string().optional() })).optional(),
});
```

Acceptance: every existing call site in `addonHandler.ts` goes through the one shared parse function; no remaining bare `JSON.parse(...) as AddonPackageJson` anywhere in the addon system; a manifest that fails validation produces a specific, addon-name-and-field-attributed log message and that addon is skipped (not a generic crash, not a silent partial load).

### B2. Permission contract — open the closed union so addons can register real permissions

Today: `Permission` in `src/handlers/permissions.ts` is a closed string-literal union covering only core panel permissions; `registerPermission(permission: Permission)` therefore cannot legally accept anything an addon declares, and the permission list itself is a single in-memory array populated by a fixed set of module-load-time calls.

Required:

- Widen `Permission` so it can represent addon-namespaced strings while keeping every existing core permission exactly as strongly typed as it is today — a template-literal type unioned with the existing literals (`type Permission = CorePermission | \`addon.${string}\``, where `CorePermission` is the existing closed union renamed) is the shape to aim for; the exact mechanism is yours to finalize per the `no-type-casts`/`ssot-or-die` doctrine (fix the type at its source, don't cast around it).
- Add a narrow registration entry point specifically for addon-declared permissions (e.g. `registerAddonPermission(addonSlug: string, permission: string)`) that validates the permission string actually matches `addon.<addonSlug>.*` for *that exact addon* before accepting it, and rejects (loudly, logged, addon-attributed) anything that tries to claim `admin.*`, `server.*`, or another addon's namespace. This is the real enforcement of the namespace rule the manifest schema (B1) only validates syntactically.
- Drive this from the manifest's `permissions` array (B1) at load time, rather than requiring addon code to call a registration function manually — the manifest already declared them, so register them as part of loading the addon, the same moment its router gets mounted.
- Confirm where the existing `permissions` array actually feeds the rest of the app (the role/API-key permission picker UI, if one exists) and make sure addon-registered permissions actually show up there once registered — and make sure `clearAddonItems`-equivalent cleanup on unload also de-registers an addon's permissions, the same way it already clears that addon's sidebar/menu/section items, so a removed addon doesn't leave orphaned permission strings assignable to a role forever.

Acceptance: an addon can declare `permissions: ["addon.my-addon.use-feature"]` in its manifest, have it actually registered and assignable through the existing permission-checking machinery (`hasPermission`, `apiValidator`), and have it cleanly removed when the addon is unloaded — with no way for any addon to ever successfully register a permission outside its own `addon.<its-own-identifier>.*` namespace.

### B3. `AddonAPI` v2 — the full surface addons get

Today's `AddonAPI` (read it directly in `addonHandler.ts` before extending it) has: `registerRoute`, `logger`, `prisma`, `utils.{isUserAdmin, getServerById, getServerByUUID, getServerPorts, getPrimaryPort}`, `addonPath`, `viewsPath`/`desktopViewsPath`/`mobileViewsPath`, `renderView`, `getComponentPath`, and `ui.{addSidebarItem/removeSidebarItem/getSidebarItems, addServerMenuItem/removeServerMenuItem/getServerMenuItems, addServerSection/removeServerSection/getServerSections, addServerSectionItem/removeServerSectionItem/getServerSectionItems}`.

Two existing bugs to fix while you're in this interface, found by direct inspection, not speculation:

- `renderView`'s implementation calls `ejs.renderFile(viewPath, data, {}, callback)` — passing a callback makes that call asynchronous, so the function's own `return ejs.renderFile(...)` returns `undefined` synchronously every single time; the callback's return value is discarded. As written, any addon author who actually calls `api.renderView()` expecting a string back gets `undefined`. Either make it genuinely async (`Promise<string>`, using the promise-returning call form, and update every consumer/the type signature accordingly) or remove it from the documented surface in favor of the `res.render(path.join(api.viewsPath, ...))` pattern the docs already show as the primary recommendation — pick one, don't leave the broken version sitting on the public interface.
- `unloadAddon` removes a route by reaching into `(app as any)._router.stack` and matching `layer.handle.name === 'router_' + slug` — a private Express internal, accessed through an `any` cast, matched by abusing a function's `name` property via `Object.defineProperty`. This works today but is exactly what `no-type-casts` and `boundaries-validate-internals-trust` warn about: it's reaching past a real boundary (Express's public API) into an implementation detail. If you have a less fragile way to track and remove exactly the middleware layer(s) panel-main's installed Express version added for a given addon — without reaching into private internals — use it; if Express genuinely offers no public removal API and this remains the only way, at minimum stop laundering it through `any`, give it a real typed accessor, and add a comment explaining the constraint so the next person doesn't think it's idiomatic.

Add, as appropriate to where each one is actually implemented (some belong directly on `AddonAPI`, some are addon-load-time wiring done once in `loadAddons` rather than per-call helpers — use judgment, matching how the existing `ui` sub-object is structured):

- `config`: `get`/`set`/`getMany`/`setMany`/`delete`/`deleteAll` against the new generic per-addon settings table (B5) — the direct functional replacement for Blueprint's `dbGet`/`dbSet` family (Part 1, section F), scoped automatically to the calling addon's own slug so one addon can never read or write another's settings.
- `ui.registerSlot(slotId, renderFn)` / `ui.unregisterSlot(...)`, plus the two layout-wrapper registrations, against the new slot registry (B4).
- `commands.register({ name, description, handler })` and `schedule.register({ id, intervalMs (or your chosen interval shape), handler })` (B10 below; Part 1 section H), both automatically de-duplicated and cleared on addon unload/reload.
- `middleware: { isAuthenticated, apiValidator, csrfProtection }` — stable references to the already-existing core middleware (`src/handlers/utils/auth/authUtil.ts`, `src/handlers/utils/api/apiValidator.ts`, `src/handlers/utils/security/csrfProtection.ts`) so addon-authored routers can require real session auth or real API-key+permission auth without reaching into internal relative paths themselves.
- `permissions.register(permission)` as a thin, addon-scoped wrapper over `registerAddonPermission` (B2) for addons that want to register something at runtime beyond what's declared in the manifest — still namespace-enforced the same way.
- `assetsUrl` (or similar): the public base URL an addon's own `public/` folder is served at (B8, static assets), so addon-authored views can reference their own assets without hand-constructing the path.

Acceptance: every new method is exercised by the reference addon (Part 6); every method that touches storage/permissions/slots is automatically scoped to the calling addon's own slug with no way for addon code to act outside that scope by passing a different slug as an argument (don't accept an addon-slug parameter on these from addon-supplied input — close over it at registration time, the same way `addSidebarItem`/`addServerMenuItem` already close over `folder` today).

### B4. The slot registry

Build a new module (or extend `uiComponentHandler.ts` if that reads as the more coherent home for it once you're looking at both side by side) holding, conceptually, `Map<SlotId, Array<{ addonSlug: string; render: (locals: Record<string, unknown>) => string | Promise<string> }>>`, plus the two singular layout-wrapper slots described in Part 1 section C.

Required:

- A fixed, exported, documented list of valid `SlotId` values (a string-literal union, not a free-form string — this is exactly the kind of "named domain type over `Record<string, unknown>`" the maintainability doctrine asks for) covering the real pages this panel has. Don't invent slots for pages that don't exist; enumerate from the actual current view structure under `views/desktop` and `views/mobile`.
- Registration and cleanup functions that mirror the existing `addSidebarItem`/`clearAddonItems` pattern exactly, so the addon-load/unload lifecycle in `addonHandler.ts` only needs one more `clearAddonSlots(slug)`-style call alongside the one it already makes.
- The two layout-wrapper slots are singular per-addon-capability (an addon either does or doesn't wrap the dashboard/admin layout; there's no "list of wrapper contributions" the way `after-content` can have several) and must check the admin-revocable capability toggle (B14 admin UI; per Part 1 section B) before rendering, every time, not just at registration time — an admin should be able to turn a wrapper off and have it take effect on the very next request, not require a full addon reload.
- Resolve the sync/async rendering question explicitly (flagged already in Part 1, section C) before wiring real core-template include points: verify how the installed `ejs` version actually behaves with nested async rendering inside a synchronous parent render call, and choose — precompute all active slot HTML for a request before calling the main `res.render` (passing the rendered strings in as locals), or thread real async rendering through end-to-end — rather than assuming either will just work.

Acceptance: at least two distinct core view templates (e.g. the per-server console page and the admin server-edit page) get a real, working include point at a documented slot id; the reference addon (Part 6) registers content into at least one slot and into at least one layout wrapper, and disabling that addon's wrapper capability via the admin toggle removes the wrapper's effect on the next request without a full addon reload.

### B5. Generic per-addon settings store

Add a Prisma model, conceptually:

```prisma
// Illustrative — match this schema file's existing naming/casing conventions exactly (note the project's
// other models are PascalCase, e.g. `Addon`, `ApiKey` — `settings` itself is the one lower-case exception).
model AddonSetting {
  id        Int      @id @default(autoincrement())
  addonSlug String
  key       String
  value     String   // JSON-encoded
  updatedAt DateTime @updatedAt

  @@unique([addonSlug, key])
}
```

Wire it up behind `api.config.{get,set,getMany,setMany,delete,deleteAll}` (B3), each call automatically scoped to the calling addon's own slug. Build a generic admin-facing settings form, driven entirely by an addon's manifest-declared `settingsSchema` (B1) — render the right input type per declared field, validate submissions against that same declared schema (this is a real untrusted boundary: an admin's form submission) before writing through `config.set`, and don't require addon authors to hand-build an EJS settings page for the common "a handful of typed key/value options" case.

Acceptance: the reference addon declares at least one setting via `settingsSchema`, it renders correctly in the admin addon-detail page with its declared default, an admin can change it through the form, and the addon can read the new value back through `api.config.get`.

### B6. Migration system overhaul

Today: forward-only `{ name, sql }` entries, applied via `prisma.$executeRawUnsafe(migration.sql)` followed by a *separate* bookkeeping insert into `AddonMigration` — not wrapped in one transaction, so a crash between the two leaves an inconsistent state (most acutely: an `ALTER TABLE ... ADD COLUMN` migration that partially applied but never got recorded will fail on retry, since SQLite's `ALTER TABLE ADD COLUMN` has no `IF NOT EXISTS` form the way `CREATE TABLE`/`CREATE INDEX` do). And on full uninstall (`src/modules/admin/addons.ts`, the `/admin/addons/store/uninstall` route), nothing touches `AddonMigration` rows or the tables they created — they're abandoned permanently.

Required:

- Each migration's DDL execution and its `AddonMigration` bookkeeping insert happen inside one transaction, so they succeed or fail together.
- Each migration entry may declare an optional `down` SQL string (B1).
- On full uninstall, before deleting the addon's files: call the addon's `onUninstall` lifecycle hook if it declared one (B7) and let it run its own cleanup; after that, if `down` SQL was declared for any applied migrations and no `onUninstall` hook handled it, run those `down` statements in reverse order as a sensible default — but only after the admin has explicitly confirmed a destructive action in the UI (mirroring Blueprint's confirmation-before-arbitrary-script-execution posture, Part 1 section G), since this is irreversible. Only after that does the framework delete the `AddonMigration` rows for that addon.
- Serialize migration application (and the surrounding enable/disable/uninstall operations) through the in-process async lock described in B7, so two near-simultaneous admin actions against the same addon, or a manual "Reload addons" firing while an install is mid-flight, can't interleave against the same `AddonMigration` bookkeeping.

Acceptance: a forced failure injected mid-migration (in a test, or by manual verification) never leaves a table created without its bookkeeping row recorded, or vice versa; uninstalling the reference addon (which should ship at least one migration with a real `down`) actually removes its custom table, not just its files.

### B7. Lifecycle hooks — install / enable / disable / update / uninstall

Today an addon's entry point is called exactly once per load, as `(router, api) => void` (or the `export default` equivalent — both forms are already supported by the existing loader and must keep working, see Part 4's back-compat checklist).

Required, designed to keep that exact call working unmodified for every existing addon:

- Let the entry-point function optionally **return** an object of named, optional hook callbacks (`onInstall`, `onEnable`, `onDisable`, `onUpdate(previousVersion)`, `onUninstall`) instead of (or alongside) doing all of its setup inline. An addon that returns nothing or a non-object keeps behaving exactly as it does today — this is the backward-compatible extension point, not a breaking change to the call signature.
- Call `onInstall` exactly once, the first time an addon is ever loaded (no existing `Addon` database row for its slug). Call `onUpdate(previousVersion)` when an existing addon's manifest version differs from its last-recorded version, before migrations run for that load. Call `onEnable`/`onDisable` from `toggleAddonStatus`. Call `onUninstall` from the full-removal route, before any files or migration records are deleted (B6).
- Every hook call is wrapped so a throwing/rejecting hook logs clearly (addon-attributed) and does not crash the panel process or block the rest of the addon system from loading other addons.
- Run all of install/enable/disable/uninstall for a given addon through a single in-process async mutex (a promise chain or small queue is enough; this is a single Node process, not a distributed system) so they can't interleave with each other or with a concurrent `reloadAddons()` call against the same addon.

Acceptance: the reference addon implements all five hooks and logs a distinguishable message from each one; toggling it off/on and fully uninstalling it in the admin UI fires the right hooks in the right order, observably, with no crash if a hook deliberately throws (verify this with a quick manual test, not just by reading the code).

### B8. Static asset hosting + path/identity containment hardening

Implement the documented-but-missing `public/` serving (Part 1, section E): mount `express.static()` against each enabled addon's own `public/` directory at a namespaced path, in `loadAddons`/`unloadAddon` alongside the router mount/unmount, and resolve with `fs.realpathSync` to confirm the served path is still inside that exact addon's own real directory before mounting — this defeats a symlink placed inside an addon's folder pointing somewhere it shouldn't.

While you're hardening path handling, apply the same real-path-containment check (not Blueprint's literal substring-matching approach to `../`/`~`/leading-slash detection — do it correctly with actual path resolution, which this codebase's TypeScript/Node environment makes easy and Blueprint's POSIX-shell environment did not) to: the addon's declared `main` entry file (must resolve inside the addon's own directory), and the addon's `views`/`desktopViewsPath`/`mobileViewsPath` resolution.

### B9. Two concrete existing bugs to fix while you're in this code

- **View-name collision across addons.** `src/app.ts` has two separate monkey-patches (one on `ejs.renderFile`, one on `res.render`) that, when Express's own view resolution fails, fall back to scanning *every installed addon's* `views/` directory by bare filename and rendering whichever one is found first (in filesystem-read order, effectively alphabetical-by-folder-name) — meaning two unrelated addons that both happen to name a view file the same thing will silently shadow each other, with no error and no indication to either addon author that this happened. The addon's own `api.renderView` (inside `addonHandler.ts`) is already correctly scoped to that one addon's own views directory and does not have this bug — only the two global app.ts overrides do. Fix the global overrides to resolve a view *only* within the views directory of whichever addon actually owns the currently-handling route (the addon's own router-level middleware already sets things on `res.locals` per request — e.g. `res.locals.addonAnimationsDisabled` — extend that same mechanism to also record the owning addon's slug, and have the view-resolution overrides look there first), falling back to a global scan only as a last resort if you decide that fallback is still worth keeping at all.
- **"Reload addons" doesn't actually reload addon code.** `loadAddons` calls bare `require(mainFilePath)` with no `require.cache` invalidation anywhere in the file (confirm this with a direct search before and after your fix). Node's module cache means a second `require()` of the same resolved path returns the already-cached module object — so the admin-facing "Reload addons" button, which is documented as useful for picking up addon changes during development, currently cannot actually pick up a code change to an addon's own entry file or anything it required. Fix this by tracking which cache keys get newly populated during an addon's own `require()` call and deleting exactly those keys before re-requiring on reload (a blunt `delete require.cache[require.resolve(mainFilePath)]` alone won't catch the addon's own internal submodules if it has any) — confirm the fix with an actual before/after manual test (edit an addon's source, click reload, observe the new behavior take effect without a full process restart), not just by reading the code.

### B10. Console commands and the scheduler

Per Part 1 section H: build `api.commands.register({ name, description, handler })` and a small internal scheduler behind `api.schedule.register({ id, ..., handler })`. Both must de-duplicate by a stable id across reloads (clear an addon's previously-registered timers/commands before re-registering on every `loadAddons` pass, exactly the way `clearAddonItems` already does for UI items) so repeated "Reload addons" clicks never leak duplicate timers or duplicate command registrations. Decide and implement at least the admin-UI-triggered delivery mechanism for commands (a button per registered command on the addon's detail page, calling the handler and showing the result); treat a genuine terminal-invocable CLI entry point as a stretch goal if time allows, per the tradeoff already laid out in Part 1.

### B11. Dependency declarations and load order

Per B1's `dependencies` field: at load time, before mounting any addon's router, build the dependency graph from every enabled addon's manifest, resolve a load order via topological sort, and refuse to load (with a specific, addon-attributed, admin-visible error — not a silent skip) any addon whose declared dependency is missing or disabled. This is new capability beyond Blueprint (Part 1, section I) — document it as such.

### B12. Compatibility/version checks against the running panel

Per B1's `engines.panel` field: compare against the panel's own version at load time using a real version-range comparison, warn (not block) by default with a clear, specific admin-facing message when there's a mismatch, and add an admin-configurable strict mode that hard-blocks instead. Check `src/handlers/updater.ts` for any existing version-reading or version-comparison utility before writing a new one — reuse it if it exists, for the same single-source-of-truth reason as everywhere else in this document.

### B13. Hardening the existing install pipeline

`src/modules/admin/addons.ts`'s `runInstall`/`isSafeCommand` allow-lists command *prefixes* (`npm install`, `cp `, `mv `, `mkdir `, etc.) and runs them via `execFileAsync(bin, args, { cwd: workDir })` — but never validates the individual *arguments* of an allow-listed command. A `cp`/`mv` entry in a remote `install.json`'s `commands` map can use a relative-path argument like `../../../somewhere` to write or move a file outside `workDir` despite `cwd` being scoped there; only the *bin* is checked, not where its arguments point. Fix this by resolving every path-like argument of an allow-listed command against `workDir` (`path.resolve(workDir, arg)`) and rejecting the entire install with a clear error if any resolved argument falls outside `workDir` — do this with real path resolution, not string pattern-matching against `../`, which is easy to get wrong (and which is exactly the approach Blueprint's own shell-based installer uses out of POSIX-shell necessity, Part 1 section A closing note — you have a better tool available here, use it). This is the one concrete, high-value security fix in the existing store pipeline; treat anything further (package signing/checksums on the cloned repo content) as a lower-priority nice-to-have, not a blocker for this task.

### B14. Admin UI additions

Tag this section for `impeccable` per the skills-usage instructions above. At minimum, the addon detail surface (new, or folded into an expanded `/admin/addons` list-item) needs to show and let an admin act on: the addon's declared identifier/version/compatibility status (with a clear, non-color-only indicator when `engines.panel` doesn't match), its declared capabilities with individual on/off toggles wired to the per-addon capability store, its auto-rendered settings form (B5), its registered slots/permissions/commands (so an admin can actually see what an addon does without reading its source), and an explicit, clearly-worded confirmation step before uninstall that states the destructive consequence (custom tables/data will be removed if the addon declares cleanup behavior; otherwise they may be orphaned) rather than a bare "Uninstall" button with no further confirmation.

## Part 3 — Security checklist

Go through this explicitly; each item should be individually verifiable, not just "addressed in spirit":

- [ ] Addon manifests are parsed through one shared, Zod-validated function (B1) at every call site; no remaining bare `JSON.parse(...) as <interface>` cast anywhere in the addon system.
- [ ] An addon's declared `identifier` must equal its folder name when both are present; identifiers are validated against the same character-set/length/reserved-word discipline described in Part 1 section A.
- [ ] No addon can register a permission outside `addon.<its-own-identifier>.*` (B2) — verify this by attempting it from the reference addon's test/dev path and confirming it's rejected.
- [ ] Every new `AddonAPI` method that touches storage, permissions, slots, commands, or schedules is scoped to the calling addon's own slug by closure, not by a slug argument the addon supplies (B3) — verify there's no method where one addon could pass another addon's slug and act on its behalf.
- [ ] An addon's `public/` static assets and `main`/`views` paths are containment-checked with real path resolution (`fs.realpathSync` / `path.resolve` + a prefix check against the addon's own real directory), not string-matching against `../` (B8).
- [ ] The `cp`/`mv` argument path-traversal gap in `src/modules/admin/addons.ts`'s `runInstall` is closed: every path-like argument of an allow-listed command is resolved against `workDir` and rejected if it points outside it (B13).
- [ ] Destructive actions (full uninstall, any `down`-migration rollback not handled by an addon's own `onUninstall` hook) require an explicit admin confirmation step in the UI, with copy that states what will be lost (B6, B14) — never a single click with no confirmation.
- [ ] Install/enable/disable/uninstall operations against a given addon are serialized through the in-process lock (B7) so two concurrent admin actions, or a reload firing mid-install, can't corrupt `AddonMigration` bookkeeping or leave an addon half-loaded.
- [ ] The view-name collision bug (B9) is fixed: two addons with identically-named view files no longer silently shadow each other.
- [ ] Documentation (Part 5 below) states plainly, without hedging, that addons run with full privileges and are not sandboxed, matching the trust-model framing in Part 1 section K — don't let any doc or UI copy imply otherwise.

## Part 4 — Backward compatibility checklist

- [ ] An addon whose entry point is exactly `(router, api) => void` (or `export default` of the same), with a `package.json` containing only the fields documented today (`name, version, description?, author?, main?, router?, enabled?, migrations?` with `{ name, sql }` migration entries) loads, runs, and migrates identically to how it does today — no new required manifest field breaks it.
- [ ] An addon manifest with no `identifier` field defaults to the folder name, exactly as today's loader already implicitly treats the folder name as the addon's identity (via `addon.slug` keyed on `folder`).
- [ ] An addon entry point that returns nothing, or returns something that isn't a plain object of hook callbacks, is treated exactly as it is today — the lifecycle-hooks addition (B7) is purely additive.
- [ ] The existing `ui.add*`/`remove*`/`get*` methods on `AddonAPI` keep their exact current signatures and behavior; the slot registry (B4) is a new, separate surface, not a replacement.
- [ ] The existing `/admin/addons*` and `/admin/addons/store*` routes in `src/modules/admin/addons.ts` keep working exactly as documented in `docs/specsheet.md` today; new functionality is added alongside, not by changing existing route contracts.
- [ ] Run the full existing test/typecheck/lint suite (and the `fallow` audit script per the skills section) against an addon built only against the pre-existing documented contract, in addition to the new reference addon, before calling this done.

## Part 7 — Suggested delivery order

Doing this in one giant change is a bad idea; sequence it so each phase is independently verifiable:

1. **Contracts first, no behavior change yet:** the manifest Zod schema and shared parse function (B1), the `Permission` type widening plus namespace-enforced registration (B2) — get these in and have every existing call site use them, with the existing system behaving identically from the outside.
2. **Fix the three concrete existing bugs** (B9's two bugs, plus the migration transaction-wrapping in B6) — these are bug fixes independent of any new capability, land them on their own.
3. **Storage and lifecycle:** the `AddonSetting` model and `api.config` (B5), the lifecycle hooks and the in-process lock (B7), uninstall-time cleanup (B6's remaining half).
4. **The slot registry and at least two real core-template include points** (B4) — the highest-value, highest-risk piece; resolve the sync/async rendering question early in this phase, before wiring more than one include point, so you're not redoing work.
5. **Static assets, commands, scheduler, dependencies, compatibility checks** (B8, B10, B11, B12) — these are largely independent of each other and of the slot work; sequence by whichever unblocks the reference addon fastest.
6. **The install-pipeline security fix** (B13) — small, self-contained, do it whenever convenient, but don't ship without it.
7. **Admin UI** (B14, via `impeccable`) and **the reference addon** (Part 6) together, since the reference addon is what you'll use to manually verify the UI actually reflects real addon-declared data rather than placeholder content.
8. **Documentation** (Part 5) last, once every contract it describes is final — but don't skip it because it's last.
